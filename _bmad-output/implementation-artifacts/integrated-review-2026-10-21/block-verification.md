## Other findings

- The 55-second refresh change permits a delayed marked proxy response to overwrite freshly rotated tokens. `lib/server/session/session-routes.ts:66` now refreshes when 55 seconds or less remain. A marked proxy request can begin with 56 seconds remaining, wait three seconds for upstream response headers, and finish after another tab has refreshed through a ping at 54 seconds remaining. `lib/server/proxy/handler.ts:147` calls `recordSessionActivity` with only `checkedAt`; because `lib/server/session/activity.ts:9` defaults `completedAt` to `at`, both guards at line 12 check the old start time and line 15 re-seals the old access/refresh tokens. The late cookie can replace the rotated cookie and break the next refresh. The named-op caller supplies its completion clock (`lib/server/named-op.ts:268`) but the proxy does not. I read the proxy activity tests at `lib/server/proxy/handler.test.ts:380–492`: the 31/55/56-second cases all use the fixed `NOW` handler at line 34, so none exercises elapsed time across the new refresh boundary. The new long-operation test at `lib/server/named-op.test.ts:406` covers only the named-op caller. A repo-wide symbol/import-reference search for `recordSessionActivity`, `canRenewLastSeen` and `createRefreshHandler` found no test that combines a delayed proxy activity response with the earlier refresh boundary. Pass the completion clock in the proxy and add a handler-level regression test that advances the injected clock while the upstream response is held, then asserts that the proxy returns its operation result without an old-token Set-Cookie.
